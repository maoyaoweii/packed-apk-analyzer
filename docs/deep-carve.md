# deep_carve：从加固 DEX 里系统性还原字符串池

配套工具：[`deep_carve.py`](../deep_carve.py)

## 为什么需要它

`apk_analyze.py` 用正则从加密流里"雕刻"类描述符，能拿到类名，
但那是碰运气——只要字节序列长得像 `Lcom/xxx/Yyy;` 就算命中，
既可能漏，也可能把日志文本误当类名。

这一轮做了字节级复核，发现主 DEX 的 101.8 MB 载荷**不是 AES 密文**：

```
前 4MB 字节频次：0x00 占 33%，0x01 > 0x02 > 0x03 ... 递减
619 段 >=64 字节的全 0，最长 4742 字节
```

AES 密文应该 256 字节均匀分布、熵≈8、无长 0 串。这个分布是
**DEX 字节码被打散重排**的特征：小端索引、大量零填充、字符串池与代码段混排。

关键证据，`0x30b600b` 附近：

```
\x00\x1a--==--- 调用finish触发了close回调\x00
\x1b--==---- new unreg sensor: \x00
\x17--compiler-filter=speed\x00     ← 0x17=23，正好是该串长度
\x0b--dex-file=\x00
```

`[uleb128 长度][UTF-8 内容][\x00]` 连续排列，正是 DEX `string_data` 的原始格式。
说明真实 DEX 的数据大部分还在，只是被壳按自定义布局拆开了。

## 算法

不再用正则，而是逐个解析 `string_data` 单元：

```
1. 在偏移 o 读 uleb128 → 长度 n
2. 校验 0 < n <= 64KB
3. 校验 data[p+n] == 0x00（结束符）
4. 校验 [p, p+n) 是合法 UTF-8、无控制字符、可打印
5. 从 p+n+1 继续读下一个单元
6. 只有"连续 >= 6 个都成功"才认定是真实字符串池区，收进结果
```

"连续命中"这道闸门是核心：随机数据里偶尔凑出一个合法单元很常见，
连续 6 个几乎不可能靠巧合，所以误报极低。

## 实战结果（享做笔记 7.6.1）

```
识别到 860 个连续字符串池区，共 494,743 条唯一字符串
字符串池区总覆盖 19.3 MB

member     271,344    class      103,636
other      103,608    proto       11,637
type         3,828    url            507
resource       171    text_zh         12

类描述符合计 103,636 个，归入 30 个功能域
```

模块分布里最值得注意的一点：**广告 SDK 合计约 27,000 个类**，
比自家笔记业务（4,682）+ 手写内核（6,833）加起来还多。

## 用法

```bash
python deep_carve.py classes.dex [输出目录]
```

产物：

```
out/
├── summary.json              结构化摘要（模块分布、top 包）
├── source_map.tsv            103,636 行：类 → 模块 → 包
├── str_class.txt 等          按 DEX 语义分类的字符串
├── chinese_text.txt          DEX 池里的中文
└── by_module/                30 个文件，每个功能域的完整类清单
```

## 局限

拿到的是**名字和字符串，不是方法体**。壳把 Dalvik 字节码按自己的索引表搬运过，
那张索引表在 `libctmtp.so` 里（ELF section 表被伪造、导出表被破坏），
静态读不出来。要真源码必须动态脱壳：Frida hook `DexClassLoader` /
`InMemoryDexClassLoader` 构造点，在内存里 dump 拼好的 dex，再喂给 jadx。
